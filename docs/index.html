Triage tooling for maintainers

vulnvet

A vulnerability report cites a function, a file, a line, a version. vulnvet checks whether any of them exist, at the revision the report claims to be about, and hands you the evidence.

Source on GitHub Install
Run against curl 8.4.0

Why

Disproving one sentence costs an hour

In January 2026 curl ended its six-year bug bounty, its maintainer writing that the project was “effectively being DDoSed” by AI-generated reports. The Python Software Foundation's security developer-in-residence documented the same load across CPython, pip, urllib3 and Requests. In March 2026 the Jazzband collective — 84 projects, over 150 million downloads a month — announced it was winding down, citing a flood of AI-generated spam pull requests.

Most countermeasures so far have been policy: honour-system checkboxes, closing the bounty, banning reporters. But the expensive part was never the policy. It was checking out the right tag, grepping for a function that turns out never to have existed, opening a file to count its lines, and working out whether those version numbers were ever released.

That step is mechanical. vulnvet does it in about a second, and nothing more.

Verdicts

Four answers, each with its evidence

  • VERIFIEDThe citation corresponds to the codebase. Not a judgement that the vulnerability is real — only that the reporter is describing code that exists.
  • NOT FOUNDWe looked in the right place and it isn't there. On a symbol, a stack frame, or quoted source, this is the strong signal.
  • MISMATCHPartly corroborated. The function exists but not in that file; the file is 400 lines and they cited line 5000; the version range runs backwards.
  • UNCHECKABLEWe could not tell either way, and say so rather than guess.

Every verdict states what was searched and what was found, so you can check it by hand. A verdict you have to take on faith would defeat the point.

Checks

What it grades

ClaimQuestion
symbolsDoes the identifier appear in the tree at all? Is it defined in source, or only mentioned in release notes? A qualified citation like Engine._run_query() is split — no source line spells it that way — and checked against the owner it names.
stack framesDoes the function exist, does the file, is the line inside it, and does that function actually appear in that file?
quoted codeDo the quoted lines appear verbatim? Which ones don't?
file:lineDoes the file exist, and does it have that many lines? A cited range (src/http.c:100-260) asserts both ends, and both are checked.
filesDoes the path exist — or is there a same-named file elsewhere, or a near miss?
versionsDo those versions exist as release tags? Is the range inverted?
commitsDoes that commit exist in this repository?
CVE IDsIs the identifier well-formed, and is the year plausible? Whether it exists in the CVE database is not checked — vulnvet runs offline.
Restraint

It fails toward "cannot tell"

A tool that cries fabrication at an honest reporter is worse than no tool. Every ambiguity resolves away from accusing:

  • Proof-of-concept code is never graded. The reporter's own script is not a claim about your codebase, and searching for it would guarantee a false accusation.
  • A stack trace walks through whatever was linked in. Frames naming OpenSSL or zlib are unverifiable, not fabricated. vulnvet learns your build root from the frames that do resolve, so it knows which frames are claiming your code.
  • Environment notes are not version claims. "Tested on Ubuntu 22.04" is never checked against your release tags.
  • Uncommitted work is not a fabrication. If your checkout is dirty and the report describes code that exists on disk but is not committed yet, vulnvet says so rather than reporting it missing. It looks outside the pinned revision in one direction only — to withdraw a negative verdict, never to grant a positive one.
  • Prose is not code. use_after_free is jargon, not a symbol; Node.js is a product, not a file.
  • Nothing is asserted beyond the evidence. Search results are capped, so "appears only in documentation" is only said when the result list wasn't truncated — and anything a budget skipped is named, and blocks a clean grade.

Escalating to "characteristic of fabricated reports" needs a pattern, not one slip. And the dossier carries this line every time it runs:

vulnvet grounds a report's citations against the codebase; it does not judge the vulnerability logic itself, and it cannot tell who or what wrote the report. NOT FOUND means a specific cited detail does not exist at the checked revision — give the reporter a chance to correct an honest mistake before concluding fabrication.
Install

One command, no dependencies

# from source, until it is on PyPI
git clone https://github.com/umeramin99/vulnvet
cd vulnvet && pip install -e .

Python 3.9 or newer and git on your PATH. Nothing else — no network access, no accounts, no API keys. The same report and revision always produce the same dossier.

# the common case
vulnvet report.md --repo ~/src/myproject --rev 8.4.0

# straight from a GitHub issue
gh issue view 1234 --json body -q .body | vulnvet - --repo .

# a dossier to paste into the ticket
vulnvet report.md --repo . --format markdown -o dossier.md

There is also a GitHub Action that vets reports as they arrive and posts the dossier as a comment, and a Python API if you are building your own triage flow.

Limits

What it cannot do

It is not an AI detector. It cannot tell you who wrote a report. A careful human can write an ungrounded one, and a fabricated one can cite real symbols.

It does not judge exploitability. A perfectly grounded report can describe a non-issue. That judgement stays with you — a clean dossier means the citations are real and the report deserves a human read.

Some real code is invisible to a search. curl genuinely builds SSL_RSA_WITH_RC4_128_MD5 out of SSL_##num_wo_prefix, and no grep will find it. vulnvet flags that risk when it sees token pasting, but read the evidence line before acting.

Padding is narrowed, not solved. Listing real filenames is free, so only claims that show the reporter read the code count toward a clean grade. Someone willing to cite genuinely real symbols around a false conclusion will still score well.
